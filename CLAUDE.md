# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

## Critical context

**This directory is a live production system.** `python-scheduler.service`,
`server-monitor.service`, `watchdog-daemon.service`, and 16 `service-*.service` units are
running under systemd right now, executing real data pipelines and writing to files here.

Consequences for any change:

- Editing `config.json` or `services_config.json` affects running services immediately.
- Do **not** `rm` active `.log` files — processes hold open handles, so no space is
  reclaimed and writes continue to a deleted inode. Truncate: `: > logs/Name.log`
- Before deleting or renaming any file, check whether a live unit references it:
  `grep -rn "<filename>" config.json services_config.json systemd/`
- Verify services survived a change: `systemctl is-active python-scheduler.service`

## Architecture

Two schedulers run **simultaneously**. Identify which owns a service before changing it.

**Wrapper architecture** (current direction) — one process and one systemd unit per service:
`services_config.json` → `service_wrapper.py <name>` ×16 → `logs/<name>.log` + `state/<name>.json`,
supervised by `watchdog_daemon.py`. Units are generated by `wrapper_generator.py` into `systemd/`.

**Centralized scheduler v2** — one process, 60s loop, SQLite state:
`config.json` → `scheduler_v2.py` → `lib/` → `scheduler_state.db`

`lib/` modules: `state_manager` (thread-safe SQLite), `circuit_breaker` (stops endless
retries), `health_monitor` (kills stuck processes), `service_executor` (subprocess handling),
`config_validator` (pre-flight validation).

Supporting: `server_monitor.py` (disk/rclone/MySQL → Discord alerts), `discord_bot.py`
(notification module), `checkDisk.py`, `rclone_monitor.py`, `sync_mocap_files.py`,
`emergency_log_cleanup.py`.

## Configuration

The two config files are **not interchangeable**:

- `services_config.json` — nested (`execution`, `health`, `retry`, `logging`); used by
  wrappers, watchdog, and generator.
- `config.json` — flat service list; used by `scheduler_v2.py`. Keys: `service_name`,
  `executable`, `path`, `working_dir`, `interval_minutes`, `time_or_minute`
  (`"minute"` | `"time"`), `scheduled_time`, `timeout_minutes`, `execute_immediately`.

Adding a service to both files schedules it twice. Pick one owner.

## Commands

```bash
python3 scheduler_v2.py --dry-run          # validate config, execute nothing
python3 service_wrapper.py Check_Disk      # run one wrapper in foreground
python3 wrapper_generator.py               # regenerate systemd units from config
python3 -m pytest tests/ -v                # test suite
bash setup_systemd_services.sh             # install/refresh all units
```

Diagnostics:

```bash
systemctl list-units 'service-*'
journalctl -u python-scheduler.service -f
tail -f logs/<Service_Name>.log
cat state/<Service_Name>.json
```

## Conventions

- Service paths inside `config.json` / `services_config.json` are absolute and
  host-specific (`/web`, `/web/zin`, `/home/gomer/viconSync`). They belong to the jobs,
  not to this tree.
- `scheduler_v2.py` and `lib/` are relocatable: they derive their config, state DB and
  log paths from the checkout's own location, overridable with `PYTHONCRON_HOME` and
  `PYTHONCRON_STATE_DIR`. On production both resolve to `/home/gomer/pythonCron`, so
  nothing moved. Do not reintroduce a literal `/home/gomer/pythonCron` there.
  `service_wrapper.py`, `watchdog_daemon.py` and the standalone job scripts still
  hardcode it.
- Secrets come from the environment, loaded from `/web/zin/.env`
  (`DISCORD_BOT_TOKEN`, `DISCORD_CHANNEL_ID`, `DISCORD_WEBHOOK_URL`).
  Never hardcode credentials — nothing in this repo contains any today.
- `logs/`, `state/`, `scheduler_state.db`, and `__pycache__/` are gitignored runtime data.
  Do not commit them.
- Service names differ between systems: `config.json` uses spaces ("Get Themas"),
  `services_config.json` and state/log filenames use underscores (`Get_Themas`).
